## 一、事件循环的本质

事件循环是**宿主环境**（浏览器、Node.js）实现异步非阻塞调度的核心机制。它负责协调：

- 调用栈（Call Stack）
- 任务队列（Task Queues）
- 微任务队列（Microtask Queue）
- 渲染时机（仅浏览器）
- 各种 I/O、定时器、事件回调

关键点：**V8 只负责执行 JS、管理调用栈和内存，不实现事件循环。**  
浏览器的事件循环由 HTML 规范定义；Node.js 的事件循环由 libuv 驱动。

## 二、浏览器事件循环

### 1. 核心组成

- **调用栈**：执行同步代码。
- **任务队列（Task Queue）**：存放“任务”，社区俗称“宏任务”。
- **微任务队列（Microtask Queue）**：存放微任务，只有一个。
- **渲染步骤**：在合适的时机更新页面。

### 2. 任务源与任务队列（重点）

浏览器不是把所有“宏任务”随便塞进一个队列，而是按**任务源（Task Source）** 分类。

> **规则：每个任务在创建时都会指定一个任务源，任务源关联到特定的任务队列。**

常见任务源与队列：

| 任务源         | 常见任务                                | 说明           |
| -------------- | --------------------------------------- | -------------- |
| 定时器任务源   | `setTimeout`、`setInterval` 回调        | 到期后入队     |
| 用户交互任务源 | `click`、`keydown`、`scroll` 等事件回调 | 通常优先级较高 |
| 网络任务源     | `fetch`、`XMLHttpRequest` 回调          | I/O 完成后入队 |
| 消息通道任务源 | `MessageChannel`、`postMessage`         | 跨上下文通信   |
| 历史遍历任务源 | `history.back()` 等                     | 导航相关       |
| DOM 操作任务源 | 某些 DOM 回调                           | 规范分类       |

**浏览器如何决定放入哪个队列？**  
创建任务时指定任务源，任务源再关联到对应的任务队列。  
同一个任务源的任务必须按顺序执行；不同任务源可能对应不同队列。

**事件循环如何选择队列？**  
规范没有规定固定优先级，但浏览器实现通常有调度策略：

- 用户交互队列优先级通常高于定时器队列。
- 有防饿死机制，防止低优先级队列永远不执行。
- 具体选择哪个队列由浏览器实现决定。

### 3. 微任务

- **只有一个微任务队列**（每个事件循环一个）。
- 常见微任务：
  - `Promise.then / catch / finally`
  - `queueMicrotask`
  - `MutationObserver`
  - `await` 后面的代码（相当于 `then` 回调）
- **微任务检查点**：调用栈清空后，会清空微任务队列。
  - 执行过程中新产生的微任务会追加到队列末尾，继续执行。
  - 微任务不清空，不会进入下一个任务，也不会渲染。

### 4. 渲染步骤

- 渲染不是每个任务后都发生，通常按屏幕刷新率（如 60Hz）决定。
- 微任务清空后，浏览器判断是否需要渲染。
- 渲染步骤包括：
  - 执行 `requestAnimationFrame` 回调
  - 样式计算、布局、绘制
  - 执行 `IntersectionObserver` 等回调
- `requestAnimationFrame` **不是宏任务，也不是微任务**，它属于渲染步骤。
- 如果微任务一直产生新微任务，会阻塞渲染。

### 5. 浏览器事件循环一轮的大致流程

1. 从某个任务队列中取出一个任务执行。
2. 执行任务中的同步代码，调用栈清空。
3. 进入微任务检查点，清空微任务队列。
4. 判断是否需要更新渲染，可能执行 `requestAnimationFrame`、布局、绘制。
5. 进入下一轮，取下一个任务。

首次执行时，全局脚本本身就是一个任务。

## 三、Node.js 事件循环

Node.js 的事件循环由 **libuv** 实现，分阶段推进，不是简单的“宏任务/微任务”二分。

### 1. 主要阶段

| 阶段              | 作用                                      |
| ----------------- | ----------------------------------------- |
| timers            | 执行 `setTimeout`、`setInterval` 到期回调 |
| pending callbacks | 执行某些系统操作的回调                    |
| idle, prepare     | 内部使用                                  |
| poll              | 获取新 I/O 事件，执行 I/O 回调            |
| check             | 执行 `setImmediate` 回调                  |
| close callbacks   | 执行 `close` 事件回调                     |

每个阶段有自己的 FIFO 队列。进入下一阶段前，会处理 `process.nextTick` 队列和微任务队列。

### 2. 特殊队列

- **`process.nextTick` 队列**：优先级高于 Promise 微任务。
- **微任务队列**：Promise、`queueMicrotask` 等。
- Node 11+ 之后，阶段之间和每个回调后都会处理 `nextTick` 和微任务。

### 3. 常见顺序特点

- `setImmediate` 在 `check` 阶段执行。
- `setTimeout` 在 `timers` 阶段执行。
- 在主模块中，`setTimeout(fn, 0)` 和 `setImmediate(fn)` 的顺序不一定，取决于事件循环启动时间。
- 在 I/O 回调中，`setImmediate` 通常先于 `setTimeout`。

## 四、浏览器 vs Node.js 对比

| 维度                    | 浏览器                     | Node.js                      |
| ----------------------- | -------------------------- | ---------------------------- |
| 规范/实现               | HTML 规范，浏览器实现      | libuv + Node.js              |
| 任务队列                | 多个任务队列，按任务源划分 | 多个阶段队列                 |
| 微任务                  | 单个微任务队列             | 微任务队列 + `nextTick` 队列 |
| `process.nextTick`      | 无                         | 有，优先级高于 Promise       |
| `setImmediate`          | 非标准，通常没有           | 有，在 `check` 阶段          |
| `requestAnimationFrame` | 有，属于渲染步骤           | 无                           |
| 渲染                    | 有                         | 无                           |
| 定时器                  | 定时器任务源               | `timers` 阶段                |

## 五、常见任务与微任务分类

### 浏览器任务（俗称宏任务）

- `setTimeout`
- `setInterval`
- UI 事件回调（`click`、`scroll` 等）
- 网络回调（`fetch`、`XHR`）
- `MessageChannel`
- `postMessage`
- 历史导航回调

### 浏览器微任务

- `Promise.then / catch / finally`
- `queueMicrotask`
- `MutationObserver`
- `await` 后续代码

### 注意

- `setImmediate` 是 Node.js 的，不属于浏览器标准。
- `requestAnimationFrame` 不是宏任务，也不是微任务。
- `Promise` 构造函数内部是同步执行的，`.then` 才是微任务。

## 六、常见误区

1. **“V8 实现事件循环”**  
   错。V8 只执行 JS，事件循环由宿主环境实现。

2. **“宏任务队列只有一个”**  
   错。浏览器有多个任务队列，按任务源划分。规范里叫“任务”，不叫“宏任务”。

3. **“微任务是宏任务的一种”**  
   错。微任务和任务是两个独立机制。

4. **“每轮事件循环都会渲染”**  
   错。浏览器按刷新率决定是否渲染，可能跳过。

5. **“setTimeout 0 会立即执行”**  
   错。它只是尽快入队，仍需等待当前任务和微任务清空。

6. **“Node 和浏览器事件循环一样”**  
   错。Node 分阶段，有 `nextTick`，没有渲染。

## 七、简单执行顺序示例

### 浏览器示例

```js
console.log("script start");

setTimeout(() => {
  console.log("setTimeout");
}, 0);

Promise.resolve().then(() => {
  console.log("promise");
});

console.log("script end");
```

输出：

```text
script start
script end
promise
setTimeout
```

解释：

1. 同步代码先执行：`script start`、`script end`。
2. 调用栈清空，清空微任务：`promise`。
3. 取下一个任务：`setTimeout` 回调。

### Node 示例

```js
setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
```

输出顺序可能不确定，取决于事件循环启动时间。  
如果在 I/O 回调中：

```js
fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
```

通常 `immediate` 先于 `timeout`，因为 I/O 回调在 `poll` 阶段，接下来进入 `check` 阶段执行 `setImmediate`，而 `setTimeout` 要等下一轮 `timers` 阶段。

## 八、一句话总结

**浏览器事件循环**：按任务源把任务分到多个任务队列，微任务只有一个队列，每个任务后清空微任务，再按刷新率决定是否渲染。  
**Node.js 事件循环**：由 libuv 分阶段推进，`process.nextTick` 优先于 Promise 微任务，`setImmediate` 在 `check` 阶段，没有浏览器渲染步骤。  
**核心记忆**：任务源决定任务进哪个队列；微任务在每个检查点清空；渲染不是每轮都有；浏览器和 Node 不要混为一谈。
