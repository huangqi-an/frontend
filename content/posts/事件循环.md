# 事件循环：浏览器任务调度与 Node.js 阶段模型

只要写 JavaScript，迟早会遇到类似的问题：为什么 `setTimeout(fn, 0)` 没有马上执行？为什么一段 Promise 代码总排在同步代码之后？为什么浏览器里能说清顺序，放到 Node.js 却出现了不同结果？

这些问题的根源不完全在 JavaScript 语法里，而在 JavaScript 的运行方式中。语言规范定义了表达式、函数、Promise 和 Job，却没有规定浏览器如何安排点击事件、网络响应与页面渲染，也没有规定 Node.js 如何轮询文件描述符。把这些宿主环境负责调度的机制统称为“事件循环”很方便，但如果不区分边界，就很容易把社区术语当成规范结论，把某个实现的特征当成所有运行时的共同规则。

这篇文章沿着三个问题展开：任务在哪里等待、微任务什么时候清空、渲染或 I/O 阶段什么时候获得机会。浏览器部分以 HTML 规范和常见实现为基础，Node.js 部分以 libuv 阶段和 Node.js 调度规则为主线，最后再把两者放在一起比较。

## 一、先划清事件循环的边界

### JavaScript 的执行模型不是“一个线程包办所有事情”

通常说 JavaScript 是单线程语言，准确含义是：一个执行线程在同一时刻只会执行一个 JavaScript 执行上下文。同步代码进入调用栈，函数返回后从栈顶弹出；如果当前调用栈被长时间占用，其他 JavaScript 回调就没有机会开始。

但浏览器和 Node.js 并不是只有一个线程。浏览器可能用其他线程处理网络、解码和部分渲染工作；Node.js 通过 libuv 的线程池、系统异步接口以及底层事件通知处理文件、网络和定时器。真正需要串行化的是 JavaScript 回调的执行：当宿主决定执行某个回调时，它会把控制权交给 JavaScript 引擎，等回调返回后再继续调度。

因此，“单线程”描述的是 JavaScript 执行上下文不能同时在多个线程中并发运行，而不是说整个运行时只有一个线程。

### ECMAScript Job 与宿主事件循环

ECMAScript 规范定义了 Promise 反应、异步函数恢复等执行单元，并把它们称为 [Job](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#jobs)。规范会说明某个操作何时需要入队一个 Job，以及 Job 应该如何被宿主执行，但它不负责定义浏览器页面何时渲染、鼠标点击事件怎么排队、Node.js 的文件 I/O 回调在哪个阶段运行。

宿主环境补上了这层调度规则：

- 浏览器遵循 HTML 规范中的 [event loop](https://html.spec.whatwg.org/multipage/webappapis.html#event-loops)，决定何时执行任务、何时清空微任务、何时更新渲染。
- Node.js 使用 libuv 事件循环与自身的 JavaScript 层调度，把回调分配到 timers、poll、check 等阶段。
- 宿主还需要决定何时运行 JavaScript 引擎中的 Job，例如 Promise 的 `then` 回调。

这就是为什么同一段 Promise 代码在浏览器和 Node.js 中通常表现相近，但 `setTimeout`、`setImmediate`、渲染回调却可能有完全不同的规则。

### V8 负责执行，不负责宿主事件循环

V8 是 JavaScript 引擎，负责解析、编译、执行代码，管理调用栈、堆和垃圾回收，并提供 Job 与微任务相关的宿主接口。但它不会实现浏览器的点击任务队列、页面布局与绘制，也不会自己实现 Node.js 的 libuv 阶段循环。

所以“V8 实现了事件循环”并不准确。更严谨的说法是：V8 负责执行 JavaScript，宿主环境负责安排什么时候调用 V8；浏览器和 Node.js 再分别定义自己的任务、阶段和渲染/I/O 调度。把 V8、宿主和规范分层之后，很多“为什么这个 API 的顺序不一样”的问题就会变得清楚。

## 二、浏览器事件循环

### 从调用栈开始

浏览器执行一段脚本时，会先把全局脚本中的同步语句放入当前执行上下文。函数调用会形成新的执行上下文并压入调用栈，返回时弹出。只要调用栈没有清空，浏览器就不会开始处理下一项普通任务，更不会进入渲染阶段。

```js
function first() {
  console.log("first");
  second();
  console.log("first end");
}

function second() {
  console.log("second");
}

first();
console.log("script end");
```

输出顺序是：

```text
first
second
first end
script end
```

这段代码没有异步操作，但它展示了最基本的调度事实：调用栈决定了当前哪一段 JavaScript 可以先执行。异步 API 之所以能“不阻塞”，不是因为 JavaScript 同时执行了两段代码，而是因为宿主保存了后续回调，等调用栈清空后再找机会执行。

### 任务、任务源与队列

HTML 规范使用 **task** 表示宿主安排的一段工作，例如执行定时器回调、派发一个事件、处理网络响应。社区常把这类任务称为“宏任务”，但规范本身并不会把它们叫作 macrotask。这个俗称可以帮助理解，但不应被误读为规范中存在一个唯一的宏任务队列。

更准确的模型是：

1. 创建任务时要指定一个 **task source**，也就是任务来源。
2. 同一个 task source 关联到某个任务队列。
3. 事件循环从任务队列中选择一个任务执行。
4. 同一个任务队列中的任务按照排队顺序执行；不同任务源之间没有统一的跨队列顺序。

常见任务源包括：

| 任务源                        | 典型任务                             | 需要理解的重点                     |
| ----------------------------- | ------------------------------------ | ---------------------------------- |
| timer task source             | `setTimeout`、`setInterval` 回调     | 定时器到期后才可能入队             |
| user interaction task source  | `click`、`keydown`、部分输入事件     | 用户操作产生的回调通常需要及时响应 |
| networking task source        | `fetch`、`XMLHttpRequest` 的完成处理 | 网络完成和 Promise 回调不是同一层  |
| posted message task source    | `MessageChannel`、`postMessage`      | 跨上下文通信也会产生任务           |
| history traversal task source | 历史导航相关回调                     | 属于另一个任务来源                 |

规范让实现可以选择执行哪个任务队列，因此不能仅凭“宏任务”三个字推导出所有浏览器的固定优先级。浏览器通常会让用户交互保持较好的响应性，也可能设置防饥饿策略，但这些属于实现策略，不是语言层面的保证。

### 微任务队列与微任务检查点

微任务不是另一种“更小的宏任务”，而是独立于任务队列的调度机制。浏览器完成一次 JavaScript 执行并准备处理下一项任务时，会执行 [microtask checkpoint](https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint)：只要微任务队列中还有 Job，就持续取出并执行；执行过程中新产生的微任务会追加到队列末尾，同样会在本次检查点中被执行。

这里有两个关键结果：

- 微任务不会插入到当前同步代码中间执行，它们要等待当前执行上下文栈清空。
- 微任务一旦开始清空，就不会只执行“一轮”就停；不停产生微任务会让检查点持续进行，其他任务和渲染都可能被推迟。

常见微任务来源包括：

| API                          | 何时进入微任务队列           | 说明                          |
| ---------------------------- | ---------------------------- | ----------------------------- |
| `Promise.then/catch/finally` | Promise 已兑现后安排反应 Job | 构造函数中的执行器不是微任务  |
| `queueMicrotask`             | 调用时直接排入微任务队列     | 语义最直接的微任务 API        |
| `MutationObserver`           | DOM 变更记录后安排回调       | 回调时机在微任务检查点附近    |
| `await` 后续代码             | 异步函数恢复时               | 恢复行为与 Promise Job 相关联 |

`Promise` 最容易引起误解。下面这段代码中，构造函数内部是同步执行的，只有 `then` 注册的反应才会在微任务检查点执行：

```js
console.log("A");

const promise = new Promise((resolve) => {
  console.log("B");
  resolve("C");
});

promise.then((value) => {
  console.log(value);
});

queueMicrotask(() => {
  console.log("D");
});

console.log("E");
```

输出是：

```text
A
B
E
C
D
```

执行过程可以拆成三步：先同步输出 `A`、`B`、`E`；`then` 注册的回调和 `queueMicrotask` 的回调入队；调用栈清空后，微任务按入队顺序输出 `C`、`D`。

### 微任务中的微任务

微任务检查点不是“最多执行一个微任务”的检查点。下面的例子可以说明为什么不能用简单的任务/微任务二分理解调度：

```js
Promise.resolve().then(() => {
  console.log("micro 1");
  Promise.resolve().then(() => {
    console.log("micro 2");
  });
});

Promise.resolve().then(() => {
  console.log("micro 3");
});

console.log("sync");
```

输出是：

```text
sync
micro 1
micro 3
micro 2
```

同步代码先输出 `sync`。调用栈清空后，微任务队列中已有两个 Promise 反应。执行第一个时，又在队尾加入 `micro 2`。第二个已经排队的微任务先执行，输出 `micro 3`；然后才轮到新加入的 `micro 2`。这一行为解释了为什么微任务检查点需要持续运行到队列为空，而不是只执行固定数量。

### 渲染机会与 requestAnimationFrame

浏览器不会在每一项任务之后都重新绘制页面。刷新率、页面是否可见、是否存在需要更新的样式或布局，以及实现自己的调度策略，都会影响是否出现渲染机会。规范描述的是 [update the rendering](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering) 的步骤，而不是承诺每一次事件循环都完整执行一遍渲染。

当浏览器准备更新渲染时，典型的顺序包括：

1. 执行 `requestAnimationFrame` 回调。
2. 进行样式计算、布局和绘制。
3. 把结果提交给合成和显示系统。

`requestAnimationFrame` 不是任务，也不是微任务。它属于渲染步骤中的回调，通常与下一次刷新机会绑定。因此，它和 `setTimeout` 谁先执行，不能脱离页面刷新时机给出绝对结论。

下面的代码在浏览器中通常先输出 `sync`、`micro`，但 `rAF` 与 `timeout` 的相对顺序取决于当前是否正好出现渲染机会以及浏览器调度：

```js
console.log("sync");

requestAnimationFrame(() => {
  console.log("requestAnimationFrame");
});

setTimeout(() => {
  console.log("timeout");
}, 0);

Promise.resolve().then(() => {
  console.log("micro");
});
```

如果需要在动画更新前做布局读取，应优先考虑 `requestAnimationFrame`；如果只是把回调推迟到当前同步逻辑之后，`queueMicrotask` 或 Promise 更合适；如果希望尽快让出调用栈并让浏览器有机会处理其他工作，则要区分是否需要进入渲染时机，而不是盲目使用 `setTimeout(fn, 0)`。

### 浏览器一轮事件循环的大致流程

可以用下面的简化流程图建立整体印象：

```text
从某个任务队列取出一个任务
          |
          v
执行任务中的同步代码与函数调用
          |
          v
调用栈清空，进入微任务检查点
          |
          v
清空微任务队列（包括执行过程中新增的微任务）
          |
          v
判断现在是否需要更新渲染
          |
     +----+----+
     |         |
   需要       不需要
     |         |
     v         v
执行 rAF、样式计算、布局与绘制
     |
     v
进入下一轮，继续选择任务
```

这不是一份逐字对应规范的伪代码，而是一个便于排查问题的模型。真实实现还要处理页面可见性、导航、跨源隔离代理、Worker 和多窗口等多个维度。

### 微任务饥饿与渲染阻塞

微任务本身很轻，但“一直产生新微任务”会阻止事件循环进入下一项任务，也会阻止浏览器获得渲染机会。下面的代码是一个概念性示例：

```js
let count = 0;

function spin() {
  count += 1;
  if (count < 100000) {
    queueMicrotask(spin);
  }
}

spin();
console.log("never reached until the microtask queue is drained");
```

如果 `spin` 在每一轮微任务中继续排入下一轮微任务，浏览器就没有机会处理点击、定时器或渲染，页面会表现为卡顿甚至无响应。微任务适合处理“当前操作完成后立即需要完成的收尾工作”，不适合替代长时间计算。CPU 密集型任务应考虑拆分为多个任务、使用 Web Worker，或至少安排明确的让步点。

## 三、Node.js 事件循环

### libuv 阶段模型

Node.js 的事件循环不是浏览器事件循环的复制品。它由 libuv 负责驱动底层事件循环，并通过各阶段的回调把结果交给 JavaScript。不同阶段处理不同来源的事件，进入下一阶段前，Node.js 还会处理 `process.nextTick` 队列和 Promise 微任务队列。

| 阶段              | 主要职责                                        |
| ----------------- | ----------------------------------------------- |
| timers            | 执行已经到期的 `setTimeout`、`setInterval` 回调 |
| pending callbacks | 处理部分延迟到下一轮的 I/O 回调                 |
| idle, prepare     | 内部准备与整理，通常不直接暴露给业务代码        |
| poll              | 获取新的 I/O 事件并执行相关回调                 |
| check             | 执行 `setImmediate` 回调                        |
| close callbacks   | 执行关闭事件的回调，例如连接关闭                |

每个阶段都有自己的回调队列。polls 阶段并不等同于“等待所有 I/O”，它还要在回调执行完后决定下一步是继续等待、回到 timers，还是进入 check。理解阶段顺序比记住“宏任务先于微任务”更有用，因为 Node.js 并没有浏览器意义上的单一任务队列。

### process.nextTick 不是事件循环阶段

`process.nextTick` 常被误解为“下一个 timers 阶段执行”，更准确的理解是：它把回调放进一个优先级很高的队列，在当前的 JavaScript 操作结束后、Promise 微任务之前处理。它不是 libuv 的某个阶段，也不等同于 `setTimeout(fn, 0)`。

```js
Promise.resolve().then(() => {
  console.log("promise");
});

process.nextTick(() => {
  console.log("nextTick");
});

console.log("sync");
```

在 Node.js 24 中输出：

```text
sync
nextTick
promise
```

同步代码先执行。调用栈清空后，Node.js 会先清空 `process.nextTick` 队列，再处理 Promise 微任务。递归使用 `process.nextTick` 同样可能造成饥饿，因为它会让回调持续插到 Promise 之前。

### setTimeout 与 setImmediate 的顺序

`setTimeout` 回调在 timers 阶段执行，`setImmediate` 回调在 check 阶段执行。但如果从主模块直接运行下面的代码，顺序并不稳定：

```js
setTimeout(() => {
  console.log("timeout");
}, 0);

setImmediate(() => {
  console.log("immediate");
});
```

主模块执行时，事件循环可能还没有稳定进入某个阶段。定时器是否已经到期、循环启动耗时以及平台实现都可能影响结果，因此不能把其中一个固定当成“永远先执行”。这并不代表 Node.js 的调度不可预测，而是说明这两个回调来自不同阶段，具体顺序取决于它们何时具备执行条件。

如果把代码放进 I/O 回调，顺序通常会稳定很多：

```js
const fs = require("node:fs");

fs.readFile(__filename, () => {
  setTimeout(() => {
    console.log("timeout");
  }, 0);

  setImmediate(() => {
    console.log("immediate");
  });
});
```

这段代码通常先输出 `immediate`，再输出 `timeout`。原因是 I/O 回调通常从 poll 阶段执行，接下来进入 check 阶段，`setImmediate` 先被处理；`setTimeout` 要等下一轮 timers 阶段。至于“通常”而非“绝对”，是因为真实的 I/O 完成时间和 Node.js 版本仍会影响调度，但阶段方向提供了稳定的解释。

### Node.js 中如何主动让出控制权

如果你有一批可以分片的工作，不要用 `process.nextTick` 递归排队，因为它会持续插到其他队列前面。更合适的方式包括：

- 用 `setImmediate` 把工作放到 check 阶段，给 poll 和其他 I/O 回调留出机会。
- 用 `setTimeout` 处理真正需要延迟的工作，而不是把它当作通用的零延迟让步工具。
- 用 Promise 或 `queueMicrotask` 处理当前操作完成后的短小收尾逻辑。
- 把 CPU 密集计算拆成小批次，避免长时间占据 JavaScript 执行线程。

Node.js 没有浏览器渲染步骤，所以 `requestAnimationFrame` 不适用于 Node.js。Node.js 的主要目标也不是保持动画流畅，而是让 I/O 回调、定时器和网络事件尽可能持续前进。

## 四、浏览器与 Node.js 的对比

| 对比维度           | 浏览器                       | Node.js                                   |
| ------------------ | ---------------------------- | ----------------------------------------- |
| 调度基础           | HTML 规范                    | libuv 阶段与 Node.js 调度                 |
| 普通异步工作       | 多个任务源关联多个任务队列   | timers、poll、check 等阶段                |
| 微任务             | 单个微任务队列与检查点       | Promise 微任务队列，并额外处理 `nextTick` |
| `process.nextTick` | 不存在                       | 存在，优先于 Promise 微任务               |
| `setImmediate`     | 非标准能力，通常不依赖       | 存在，在 check 阶段执行                   |
| 渲染回调           | 有 `requestAnimationFrame`   | 没有页面渲染回调                          |
| 页面渲染           | 有渲染机会时更新             | 没有浏览器渲染步骤                        |
| 定时器             | 属于 timer task source       | 属于 timers 阶段                          |
| 典型阻塞后果       | 页面卡顿、交互延迟、无法绘制 | I/O 延迟、心跳和任务处理延后              |

最重要的结论不是背下表格，而是先问“当前代码在哪一种宿主环境中运行，宿主正在处理哪个阶段或哪一种任务源”。同一个 Promise API 会在两种环境中都安排微任务，但 `setTimeout`、`setImmediate` 和渲染回调的语义并不相同。

## 五、常见误区与修正

### 误区一：V8 实现了事件循环

V8 负责 JavaScript 的执行和相关的 Job 接口，宿主负责事件循环。浏览器实现的是 HTML 调度模型，Node.js 实现的是 libuv 阶段模型。把 V8 当成事件循环的实现者，会掩盖宿主层才是调度决策者这一关键事实。

### 误区二：浏览器只有一个宏任务队列

规范使用 task source 和 task queue 描述异步工作，不同来源可以关联不同队列。任务源之间的选择顺序通常由实现决定，不能把“宏任务队列”当成一个统一的 FIFO 队列来推理所有浏览器的顺序。

### 误区三：setTimeout 0 表示立即执行

`setTimeout(fn, 0)` 只表示尽早安排定时器，不表示回调会插到当前同步代码或微任务前面。浏览器和 Node.js 还可能受到最小延迟、嵌套定时器限制、后台页面节流和系统负载影响。

### 误区四：微任务和任务只是优先级不同

微任务与任务是不同的调度机制。任务之间通过任务源和阶段组织，微任务则有独立的检查点；只有在当前执行上下文栈清空后，宿主才会处理检查点。它们不是“同一队列里的高低优先级项目”。

### 误区五：每一轮事件循环都会渲染

浏览器是否更新渲染取决于刷新率、当前是否需要绘制和浏览器实现策略。没有 DOM 变更、页面不可见或距离下一次刷新时间不足时，渲染步骤可能被跳过。动画代码应该围绕渲染机会设计，而不是假设每个任务后都会绘制。

### 误区六：Node.js 与浏览器事件循环完全一样

很多 Promise 行为相似，是因为两者都需要执行 ECMAScript Job；但浏览器有任务源、微任务检查点和渲染步骤，Node.js 有 libuv 阶段、`nextTick` 和 `setImmediate`。先找到共同语言层，再判断宿主层差异，才能避免把结论生搬硬套。

## 六、排查异步顺序的实用清单

遇到执行顺序不符合预期时，可以按下面的顺序检查：

1. 先标出同步代码，确认调用栈中的代码会按书写顺序执行。
2. 找出每一个异步 API：它产生的是任务、微任务、渲染回调，还是 Node.js 阶段回调。
3. 对 Promise 分开看构造函数和 `then`，构造函数中的代码同步执行，反应 Job 在微任务检查点执行。
4. 如果存在 `await`，把 await 之后的代码视为会在恢复时安排的后续执行，不要把它当成同步代码。
5. 在浏览器中检查是否存在渲染机会，不要假定 `requestAnimationFrame` 与定时器有固定跨队列顺序。
6. 在 Node.js 中确认代码位于主模块、I/O 回调还是某个具体阶段，并检查 `nextTick` 是否插入了更高优先级的队列。
7. 最后检查是否存在微任务饥饿、长时间同步计算或未受控的递归调度。

这套检查顺序的价值在于，它不要求一次记住所有输出结果，而是要求每一段代码都能回答：它由谁排队、进入哪个队列或阶段、在哪个检查点被处理。

## 七、总结

浏览器事件循环的核心是任务源、任务队列、微任务检查点和渲染机会。任务不属于一个统一的“宏任务队列”，浏览器可以选择任务源和队列；微任务会在检查点中持续清空；渲染不是每一轮都有，`requestAnimationFrame` 属于渲染步骤。

Node.js 事件循环由 libuv 按阶段推进。`process.nextTick` 不属于某个阶段，而是先于 Promise 微任务处理；`setImmediate` 在 check 阶段执行，`setTimeout` 在 timers 阶段执行；主模块中的二者顺序可能不确定，但 I/O 回调中的阶段方向通常更稳定。

真正可靠的调试方法不是背结论，而是分清 ECMAScript Job、宿主事件循环和具体运行时实现。只要沿着“谁排队、排队到哪里、什么时候清空、什么时候渲染或进入下一阶段”这条路径分析，大多数看似神秘的输出顺序都可以被解释。
